# CxBOM interface contracts

Version 1.0.0 (2026-09-24). Owner: ATACE Working Group.

Each contract has a JSON Schema and a valid example in its directory, and
`contracts/checks.py` runs the schema plus the rules a schema cannot state.
Every change bumps the contract's version in the same commit that changes a
producer or consumer. Run `pytest` before committing any contract change.

The three contracts let the Mac session and the Jetson session work in parallel.
The producer owns each contract. A consumer may request a change but never edits
the contract alone.

| Contract | Producer | Consumers |
|---|---|---|
| C1 measurement | Jetson `lab/harness` | cxbom.org heat field, demo dashboard, talk plots |
| C2 demo events | Jetson `lab/demo` and `cxbom proxy` | Mac `demo/dashboard`, recording pipeline |
| C3 proxy CLI, lockfile, and attestation | Mac `cxbom/` | Jetson `lab/demo`, GitHub Action (post-talk) |

Rules shared by all three:

- UTF-8 JSON. Timestamps are RFC 3339 UTC. Hashes are lowercase hex SHA-256.
- No hostnames, usernames, home paths, IP addresses, or account names in any
  output. Hardware is named by class (`jetson-agx-orin-64gb`), never by host.
  The anonymity gate scans every emitted file before it is committed or published.
- A consumer must reject a document whose `contract.version` major number it does not support.

## C1 measurement (`contracts/measurement/2.0.0`)

Files: `measurement/measurement.schema.json`, `measurement/example.measurement.json` (synthetic,
generated by `measurement/make_example.py`). The design is `docs/design/lab-j1.md` section 9.

One file per J1 run and model: `lab/results/<run-id>-<model>.measurement.json`. It records, per
design cell and rung, the rule's attention share at the final prompt position and the disclosure rate.

- `run.kind` is `pilot` or `confirmatory`. A pilot file carries only exploratory evidence.
- `run.preregistrationSha256` is the sha256 of the locked `lab/PREREGISTRATION.md`. It is null only
  for a pilot.
- `run.environment` is a closed allowlist of basenames with hashes. `run.hardware` is a class.
- `judge.canarySetSha256` is the hash of the canary set. No canary appears in any file.
- `attentionDefinition.aggregation` is `ratio of means`, with sink positions excluded and the
  remainder renormalized. `sinkBins` lists the field columns that hold sink tokens.
- Each `ladder` entry names its `cell` (placement, content, defense, span, regime) and `rung`
  (`0`, a demonstration count, or `R-ref`). `shots` equals the rung for numeric rungs.
- Quantities per entry: `attackSuccess` (with `clusterCi95` and `descriptiveWilson95`),
  `primaryRuleShare` (with and without sinks inside the rule, and `clusterCi95`), `attentionMass`
  (`sink`, `ring0`, `ring1`, `ring2`, summing to 1) and `attentionMassDetail` (segment masses,
  summing to 1). `field` is optional.
- **Evidence.** The entry and every quantity carry `evidence` (`confirmatory`, `gatekept` or
  `exploratory`) and `hypothesisIds`. Confirmatory needs Phi ids (`H1` to `H4`), gatekept needs Qwen
  ids (`Q-H1`, `Q-H2`), and exploratory carries none. Descriptive quantities are always exploratory.
  The entry's evidence is the strongest of its quantities.
- **Consumer rule.** Every consumer shows an "exploratory" badge on any quantity whose evidence is
  not `confirmatory`, following the precedent of `synthetic`.
- `checks.check_measurement` enforces the producer side: sums, the Wilson recomputation, intervals
  that contain their estimate, rung order within a cell, and the evidence rules. A consumer rejects
  a document whose major version it does not support.

## C2 demo events (`contracts/events/1.4.0`)

Files: `events/event.schema.json` (one line of the merged stream),
`events/sidecar-event.schema.json` (one line of a proxy's `--events` sidecar,
before merging), `events/example-rug-pull-gate-on.events.jsonl` (a synthetic
run of the proxy blocking a rug-pull, usable for dashboard development,
regenerated by `events/make_example.py`).

A stream of JSON objects, one per line. During recording the Jetson serves it as
Server-Sent Events at `GET /events` on the local network, and it always writes
the same lines to `lab/runs/<run-id>.events.jsonl` so any run replays exactly.
The dashboard renders from the stream or from the file with identical results.

Envelope:

```json
{"v": 1, "seq": 17, "t": 12.480, "run": "demo-2026-10-12-take3", "type": "gate_decision", "data": {}, "prev_sha256": "<hex, or null at seq 0>"}
```

`seq` increases by one with no gaps. `t` is seconds since `run_started`, monotonic.

`prev_sha256` chains every line to the one before it: the value at seq `n`
(`n >= 1`) is the lowercase hex SHA-256 of line `n - 1`'s exact UTF-8 bytes,
excluding its terminating newline. It is `null` at seq 0. `checks.check_events`
requires `prev_sha256` to be null only at seq 0. `checks.check_events_text`
verifies the byte-level chain over the raw lines before parsing them, because
the chain cannot be checked once JSON has discarded the original bytes. The J2
collector computes the chain as it writes the merged stream, since it is the
stream's single writer.

|---|---|---|
| `run_started` | `scenario` (`clean`, `rug-pull`, `many-shot`, `launch-pin`, `benign-update`, or `malicious-at-approval`), `gate` (`off`, `observe`, or `enforce`), `model` (id and revision), `synthetic`, `demonstration` | demo |
| `beat` | `id`, `title`, `caption` (the narration sentence, or exactly `""` for a hold), `minHoldSeconds` (the narration length for this beat) | demo |
| `tool_listed` | `serverId`, `tool`, `sha256`, `phase` (`initial` or `refresh`) | proxy |
| `tool_approved` | `serverId`, `tool`, `sha256` | J2 demo harness, after `cxbom approve` (never the proxy) |
| `tool_swapped` | `serverId`, `tool`, `oldSha256`, `newSha256`, `descriptionDiff` (unified diff text) | proxy |
| `gate_decision` | `serverId`, `tool`, `decision` (`allow`, `block`, or `would-block`), `reason`, `findingId` (optional) | proxy |
| `cxbom_emitted` | `recordPath`, `findingsOpen`, `inversionDetected`. Optional since 1.4.0: `templateOverheadTokens`, `contextWindowTokensUsed`, `findings` | emitter |
| `model_delta` | `text` (streamed output fragment) | demo |

| `exfil_attempt` | `tool`, `url`, `canaryPresent` | demo |
| `inbox_received` | `bytes`, `canaryPresent` | demo (attacker inbox) |
| `attention_frame` | `shots`, `ring0`, `ring1`, `ring2`, `ladderIndex` (points into a C1 file), `sink` and `evidence` (optional objects, shape owned by C1 2.0.0) | harness |
| `run_finished` | `outcome` (`exfiltrated`, `blocked`, `no-attack`, or `aborted`) | demo |

| `proxy_exited` | `serverId`, `exitCode` (0 to 255; a signal kill is `128 + N`) | demo |
| `proxy_stderr` | `serverId`, `text` (one line the proxy printed, already scrubbed) | demo |

The canary is never emitted in clear. `canaryPresent` is the only signal.

`gate_decision.decision` is `would-block` only in a run whose
`run_started.gate` is `observe`: the proxy found a mismatch and logged the
block it would have made in enforce mode, but forwarded the item.

`gate_decision` is a proxy event, and the proxy runs only in `enforce` or
`observe` (there is no `off` proxy mode), so `decision` pairs with the run's
`gate`. Under `enforce` a decision is `allow` or `block`. Under `observe` it is
`allow` or `would-block`, never `block`. Under `off` there is no
`gate_decision` at all, because off runs no lockfile checks and no proxy.
`run_finished.outcome` pairs with the gate too: `blocked` is reachable only
under `enforce`, since only enforce blocks a mismatch, so an `observe` or `off`
take ends `exfiltrated`, `no-attack`, or `aborted`. `checks.check_events`
enforces both pairings: it reads `run_started.gate`, rejects a `gate_decision`
whose `decision` the gate cannot produce, and rejects a `blocked` outcome
outside `enforce`. The JSON Schema cannot state either rule, because both bind
one event's value to another event's field.

`tool_approved` comes from the J2 demo harness after it runs `cxbom approve`.
The proxy never writes it, because approval happens outside a proxy session.

`checks.check_events_text` parses each line with `cxbom.jsonstrict`, so a
line holding `NaN`, `Infinity`, or a duplicate key is an error rather than a
value two readers could see differently.

`run_started.scenario` names which staged story a take tells. `clean` is the
baseline, `rug-pull` the description swapped after approval, `many-shot` the
volume attack, `launch-pin` the edited launch config, `benign-update` a
legitimate version bump whose tool description changed, and
`malicious-at-approval` a tool that was already malicious when it was approved.
The last two are the honest pair, and both run under `gate: enforce`.
`benign-update` is blocked, correctly by the rule and wrongly by intent, which
is the false-positive cost of pinning a description. `malicious-at-approval` is
not caught at all: the pin holds because the tool never changed, which is the
limit of pinning. A demo that shows only `rug-pull` overstates what approval
buys.

**A blocked legitimate update and a blocked attack carry the same `outcome`.**
`run_finished.outcome` is `exfiltrated`, `blocked`, `no-attack` or `aborted`, so
a `benign-update` take and a `rug-pull` take both end `blocked` under
`gate: enforce`. The contract conflates a true positive with a false positive
there, and the difference is not recoverable from `outcome`: it lives in
`run_started.scenario` and in the blocking `gate_decision`'s `reason`. A reader
of a published file has to read those to know which one it watched. C2 1.3.0
adds no outcome value for this, so that pair of fields is the only signal.

`gate` records the proxy's enforcement mode for the run: `off` runs with no
lockfile checks at all, `observe` checks and logs without blocking, and
`enforce` blocks a mismatch before the model sees it. `demonstration` is true
only for a run staged to teach or record a scenario. It marks a single
scripted illustration, never a rate, and is never averaged or treated as a
trial count. `attention_frame.sink` and `attention_frame.evidence` carry the
canary-sink location and the supporting evidence for an attention reading.
Both are opaque JSON objects here because their shape belongs to contract C1
2.0.0, not to C2.

Proxies do not write the merged stream. With `--events FILE` a proxy writes
sidecar events (`events/sidecar-event.schema.json`) carrying `at`, `mono`,
`proxySessionId` and a per-session `localSeq`. The J2 collector is the one live
writer of the merged stream, and it drains every open sidecar before it writes
each of the demo's own events, so a proxy event is merged ahead of the demo
event it precedes. `mono` restarts near 0 in every proxy process, so it orders
events only within one session.

Within one session the order is the sidecar's file order, which equals its
`mono` order, and the collector verifies the two agree before it writes the
session's lines: a line whose `mono` falls below the line before it in the same
session is a corrupt sidecar and stops the merge. Across sessions the order is
drain order. A session's lines land in the order the collector drained them,
and the sessions read in one drain attach in the order that drain read them. A
`launch_refused` line's `proxySessionId` is `null` (see below) and its `mono`
belongs to a process that opened no session, so it has no session order to
keep. Each null-session line lands at the drain that reads it, in the sidecar's
file order among the lines that drain reads. The collector assigns `seq` and
`t` once the order is settled, which is why it is the single writer. The merged
file and its `prev_sha256` chain are the record: the dashboard and every replay
read the file, never the sidecars, so the order the collector wrote is the
order every reader sees.

Canary redaction happens at the source. A proxy started with
`--redact-sha256` replaces any string in its sidecar events whose SHA-256
matches, or that contains a match, with `<canary>` (spec 8.7). The collector
does not redact. It verifies that no canary survives in any sidecar or demo
event before it writes the merged stream.

Each sidecar event's `data` has exactly the shape of the merged event of the
same `type`. `events/sidecar-event.schema.json` carries the same per-type
blocks as `events/event.schema.json` for its six types. `launch_refused`'s
sidecar block also constrains `proxySessionId` and `localSeq`, fields the
merged schema has no equivalent of.

`localSeq` starts at 0 for each `proxySessionId` and increases by exactly 1
per event within that session. Proxy sessions can interleave freely in one
sidecar file, so `checks.check_sidecar_events` tracks the last `localSeq` per
session rather than comparing adjacent lines, and reports a session whose
first event does not start at 0 or whose later events skip a number.

A `launch_refused` line has no session-sequence semantics of its own: its
`proxySessionId` is always `null` and its `localSeq` always 0, because it is
written before any session opens (spec 8.1). Any number of them may appear
anywhere in a sidecar file (the proxy can be relaunched against the same
`--events` path after a refusal, as the J2 demo's scenario S4 does), and each
is checked on its own, independent of every other line. A `--mode observe`
refusal that has nothing to do with the launch writes no event at all,
leaving an empty (zero-byte) sidecar file rather than no file: `--events`
still opens the file before the refusal happens.

The dashboard's terminal and attestation panes each have two sources. When it
replays a recorded take it reads the run bundle's files, the asciinema cast
and the C3 attestation logs. When it follows a live take it reads
`proxy_stderr`, `proxy_exited` and `attestation_appended` from the stream. The
demo harness writes all three, never the proxy: the harness already owns the
child's stderr, its exit status and the attestation file, and reading them
there leaves the proxy's sidecar queue for proxy events. A take that carries
both sources must carry the same lines in both, which is a stronger check than
either source alone. `checks.check_attestation_agreement` enforces it for the
attestation pane: it takes one server's C3 log text and the merged stream, and
reports a difference in line count, kind order, sequence number, or per-line
content hash. The `summary` field is prose written for the pane and is not
compared. It takes one log, so a take that restarts a proxy against the same
server passes each log with that log's slice of the stream, split at the
session line. Handed the whole stream for such a take it says so, rather than
reporting a line-count difference a reader would take for a disagreement.

`attestation_appended.sha256` is the lowercase hex SHA-256 of the C3 log
line's exact UTF-8 bytes, excluding its terminating newline, which is the same
convention `prev_sha256` uses. The demo harness has those bytes already, since
it reads the attestation file to write the event. The hash is what makes the
agreement check bite: C3 kind sequences are stereotyped (session, protocol,
server, verdict, end), so two different takes of the same server match on kind
and sequence as a matter of course, and a pane built from take B would
otherwise certify as agreeing with take A's log. For the same reason
`check_attestation_agreement` takes the log's text and not its parsed lines.
The hash covers bytes, and re-serializing a parsed line does not reproduce
them: `cxbom.attestation` writes with `ensure_ascii=False`, so a non-ASCII
value comes back as an escape.

The pane carries one `attestation_appended` per line the reader framed, and a
short-write fragment is not one of them. A C3 reader tolerates a single
unparseable line when the line after it is `end` with reason `attestation-io`,
the writer's recovery record after a partial append. The fragment has no
`kind`, no `seq` and no meaning to render, so the pane skips it and resumes
with the recovery `end` line, which is a complete line and does get its own
event. A harness that emits an event for the fragment leaves the pane one
longer than the framed log, which `check_attestation_agreement` reports as a
line-count difference. This is the one log shape a real short write produces,
so getting it wrong shows up as a bogus disagreement on the pane that carries
the demo's central claim.

`attestation_appended.seq` follows C3 2.0.0's rule, because it mirrors a C3
log line. The session line carries `null`, since C3 starts `seq` at 1 on the
line after the session line, and every later line of the same log is
contiguous from 1. `checks.check_events` tracks the sequence per log, so two
servers attested in one take do not interleave into a single count, and a take
that restarts a proxy against one server starts that server's count over. The
session line is the restart: C3 writes one log per proxy session, and it is the
only marker of a new `proxySessionId` the merged stream carries, because
`attestation_appended` holds the C3 line's hash and not its payload.
`checks.check_sidecar_events` tracks `localSeq` per `proxySessionId` for the
same restart, so the two layers agree. Contiguity stays strict inside one log:
a gap after a session line is still an error. It also requires the value to be
an integer and not a zero-fraction float, in
C3's words, because JSON Schema's `integer` accepts `1.0` and `1.0 == 1` would
carry it past both the contiguity rule and the agreement comparison while the
two panes rendered `1.0` and `1`.

Two session lines for one server must carry different `sha256` values, and
`checks.check_events` requires it. A genuine second log has a different session
line: C3 mints a fresh `proxySessionId` per writer and records `startedAt` and
`pid`, so its bytes differ and so does the hash. A repeated session hash is one
log written into the stream twice rather than a restart, and nothing else
catches it: the sequence restart is legal, the agreement check sees one log per
slice, and the payload is not in the event to compare against the file. The
rule covers session lines only. Two restarts inside one second write
byte-identical `protocol` and `server` lines, whose `at` is second-resolution,
so a rule over every line would refuse a legal pair of logs.

`proxy_exited.exitCode` is 0 to 255, the range a POSIX wait status reports. A
proxy killed by a signal is written as `128 + N` for signal number N, so a
`SIGTERM` kill is 143 and a `SIGKILL` is 137. That is what a shell reports and
what the terminal pane shows. A harness reading a negative return code from
Python's `subprocess` maps it before writing the event, so two harnesses
cannot encode the same kill two different ways. `checks.check_events` requires
an integer here too, for the same float reason as `seq`.

### Replay on cxbom.org

The site's "Watch a session" explainer replays committed `*.events.jsonl` files
through the same renderer as the demo dashboard. That puts three extra
requirements on every file published to the site:

- It passes the anonymity gate and carries no hostnames, paths, or account names.
- Every `beat` carries a `caption` field holding the narration sentence for that
  beat. The site shows it as the step caption and the demo uses it for the voiceover.
  A caption that is exactly the empty string is a hold: the beat shows and says
  nothing for its `minHoldSeconds` (the S3 reveal still). A caption that is only
  whitespace is refused by `checks.check_events`.
- `mcp_message.summary`, `tool_swapped.descriptionDiff`, `proxy_stderr.text` and
  `attestation_appended.summary` are safe to publish. The poisoned description is
  published as text, because it is the teaching point. In all four fields every
  canary occurrence is replaced by `<canary>` before the file is written, which is
  what makes them safe to publish: the canary is never published in clear, here or
  anywhere else in the stream. The last two are free text copied out of another
  process's output, which is where an unscrubbed value reaches a file without
  anyone choosing to put it there.

### 1.3.0

Minor, backward-compatible. Every 1.2.0 line and example stays valid.

  panes: `proxy_stderr` (one scrubbed stderr line), `proxy_exited` (the exit

  already owns the child's stderr, its exit status and the attestation file,

  None of the three appears in `events/sidecar-event.schema.json`, which is
  how a reader can tell a demo-written event from a proxy-written one.
- `checks.check_events` requires an `attestation_appended` session line to
  carry a null `seq` and every later line of the same log to be contiguous
  from 1, mirroring C3 2.0.0. Per log and not per server: C3 writes one log
  per proxy session, so a take that restarts a proxy against one server starts
  that server's count over at the second session line, the way
  `checks.check_sidecar_events` already treats a restart against one `--events`
  path. A gap inside one log is still an error. `seq` and
  `proxy_exited.exitCode` must both be integers rather than zero-fraction
  floats, which the schema's `integer` alone would accept, in the same words
  `checks.check_attestation` uses.
- `checks.check_events` also requires two `attestation_appended` session lines
  for one server to carry different `sha256` values. A genuine second log has a
  different session line, since C3 mints a fresh `proxySessionId` per writer
  alongside `startedAt` and `pid`, so a repeated session hash is one log written
  into the stream twice rather than a restart. Session lines only: two restarts
  inside one second write byte-identical `protocol` and `server` lines.
- `attestation_appended` carries `sha256`, the hash of the C3 line's bytes as
  written. Kind and sequence alone identify a position in a stereotyped
  sequence, not a line, so without the hash a pane built from one take agrees
  with another take's log.
- The dashboard renders both panes from the run bundle's files when it
  replays, and from these events when it follows a live take. When both exist
  for one take, they carry the same lines, and
  `checks.check_attestation_agreement` refuses a pair that disagrees. It takes
  the log's text, because the hash is over bytes.

### 1.3.1

Patch, documentation only. Every 1.3.0 line and example stays valid. No enum,
field, required list, or `additionalProperties` rule changed, so no consumer
breaks. The schema `$id` and title carry the new version.

- Documented the collector's merge rule in full. The J2 collector is the one
  live writer of the merged stream and drains every open sidecar before each
  demo event. Within one session the order is file order, which equals `mono`
  order and is verified. Across sessions the order is drain order, with attach
  order within one drain. Each null-session `launch_refused` line lands at the
  drain that reads it. This replaces the earlier wording that ordered a
  null-session line by its arrival time. The merged file and its `prev_sha256`
  chain are the record.
- Answered how C2 reports a keyed canary that appears in a tool-call argument
  that is not a url. `exfil_attempt` reports the network exfiltration channel
  and keeps its required `url`, because the event means the secret is leaving
  by that URL. A keyed canary in a non-url argument is a rule violation, not a
  network exfiltration, and C2 reports it through the redacted
  `tool_call.arguments`, where the offending argument reads `<canary>`. The
  canary never reaches the stream in clear, because the publish check and the
  shape rule in `cxbom.canary` scan every event's data values, not only urls.
  `exfil_attempt` is not repurposed for a non-url argument: an `exfil_attempt`
  without a `url` is refused by the schema (`url` is required and
  `additionalProperties` is false), which keeps the stream from asserting an
  exfiltration that did not happen. No schema affordance is added here. A
  distinct typed signal for a non-url rule violation would be a new event, and
  this contract adds an event as a minor bump (see 1.2.0 and 1.3.0), so it
  would be 1.4.0, not 1.3.1.

  `contextWindowTokensUsed` (integers, at least 0), and `findings`, a list of
  objects with exactly `id`, `title`, `category`, `severity`, `status`,
  `cweRef` (strings), `owaspRefs` (list of strings) and `affectedComponents`
  (list of strings). A finding with an extra or missing key is a schema error
  that names the key.
  `id`, `severity`, `status` and each `owaspRefs` item carry the constraints of
  the C1 record's finding (`spec/cxbom-0.3.0.schema.json`, `definitions/finding`):
  `id` matches `^finding-\d+$`, `severity` is `critical`, `high`, `medium` or
  `low`, `status` is `open`, `mitigated`, `resolved` or `accepted`, and an
  `owaspRefs` item matches `^LLM(0[1-9]|10)$`.
- The 1.4.0 text fields (`label`, `sanitizationStatus`, `assemblyPosition` and
  every finding string) are not redacted to `<canary>`. The whole-stream canary
  scan reaches them and REFUSES the take that carries a canary or a
  canary-shaped string in one, so the take is lost rather than published.
- `checks.check_events` refuses a finding whose `affectedComponents` names a
  component the finding's own inference did not assemble. An inference is the
  run of `component_assembled` events since the previous `cxbom_emitted`.
- `checks.check_events` refuses `templateOverheadTokens` above
  `contextWindowTokensUsed` when both are present. Equal is valid. Either one
  alone is not compared.

## C3 proxy CLI, lockfile, and attestation (`contracts/proxy/2.0.0`)

Files: `proxy/lockfile.schema.json`, `proxy/example.cxbom.lock` (signed with the
published example key `proxy/example-key.pub`, regenerated by
`proxy/make_example.py`), `proxy/attestation-line.schema.json`,
`proxy/example.attestation.jsonl` (also regenerated by `proxy/make_example.py`).

The authoritative behavior is `docs/design/tool.md` v4.0 sections 6 to 8. This
contract fixes the file formats.

- **Lockfile.** Each server holds a signed `envelope`. The signature covers
  `serverId`, `lockScope`, `entrySeq`, `issuedAt`, `notAfter` and `entry`.
  Consumers verify the signature against the user's signed trust manifest. They
  refuse an `entrySeq` below the recorded high-water mark and refuse expired
  entries.
- **Lockfile times** (`issuedAt`, `notAfter`, `approvedAt`) are RFC 3339 UTC
  with an uppercase `Z`. An offset such as `+00:00` fails the schema.
- **Ignore pointers.** Each `ignoreFields[].pointer` names an exact leaf under
  `/_meta`: one or more non-empty segments, so `/_meta/a` and `/_meta/a/b` pass
  and `/_meta//a` and `/_meta/a/` fail.
- **Lock checks.** `checks.check_lock2_text` parses the text strictly (no NaN,
  Infinity, duplicate keys, integers beyond 2**53, or nesting deeper than
  128, and at most 1 MiB), then checks the schema, the canonical form, and the
  envelope binding (`serverId` equal to its key, `lockScope` equal to the
  lock's) for every server in the lock. The library's
  `lockfile.verified_entry` checks the binding only for the server it was
  asked to verify, and additionally verifies the signature, the time window,
  and the high-water mark.
- **Attestation.** Write-ahead JSON Lines, one proxy session per file, in the
  user state directory. The first line is `session`. Later lines carry a
  contiguous `seq` from 1. An `end` line, if present, is last.
- **Attestation framing.** A reader splits the file on `\n`. A final line
  with no trailing newline is a partial write and is ignored. An empty
  complete line is an error. Exactly one unparseable line (the fragment a
  failed write left behind) is tolerated, and only when it is immediately
  followed by the log's final line and that line is `end` with reason
  `attestation-io`. Every other line must be strict JSON (no duplicate keys,
  no NaN). `checks.check_attestation_text` applies these rules and then
  `checks.check_attestation`, the same as the library's
  `attestation.read_log` followed by `attestation.check_log`.
- **Server line first.** The proxy writes the `server` line before any
  `verdict` line (spec 8.5). A `pinned-match` verdict that arrives before any
  `server` line leaves its item `unverified`, and any `server` verdict other
  than `pinned-match` blocks every item.
- **Verdict hashes.** `sha256` on a `verdict` line is 64 lowercase hex, and may
  be null only when the verdict is `uncanonicalizable`. `storeRef` on `server`
  and `verdict` lines is null or 64 lowercase hex.
- **State lines.** `state` is `not-listed`, `blocked`, or `unverified`. A
  state line never grants `allowed`: only a `pinned-match` verdict under a
  `pinned-match` server line does. `itemType` and `name` may each be `*`,
  which matches every item type or every name already seen. A state line with
  no `*` also creates the item when it has not been seen. The proxy refuses
  items literally named `*`.
- **The proxy never writes a CxBOM record.** The emitter writes records.
